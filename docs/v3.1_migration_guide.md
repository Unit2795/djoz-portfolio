# Version 3.1 Migration Guide

## Links

[Return to main README.md](../README.md) | [Setup Guide](./setup.md) | [Deployment Guide](./deployment.md) | [Live Demo](https://acedev.us/) | [Use This Template](https://github.com/Unit2795/djoz-portfolio/generate)

## Overview

This guide walks you through upgrading from Version 3.0 (V3.0) to Version 3.1 (V3.1) of the portfolio.

This is an in-place upgrade: merge the template, update a few local settings, and deploy. Nothing is destroyed.

V3.1 simplifies the code and fixes bugs in analytics, the analytics dashboard, the site's scripts, the Lambda build and the deploy workflow. Most of it needs no action. The changes you need to act on are:

- The analytics event format changed, so the Lambdas must be deployed before the site. The deploy workflow already does this.
- The dashboard stores its data in a new table, so you need to sync it once.
- Terraform uses a new provider, `hashicorp/archive`, so local Terraform needs `terraform init` again.
- If you changed or added site components, the `customEl` helper they used is replaced by `elementProps` and `PropsElement`.

## Step 1: Merge the Template

1. Create a new branch, then merge the template (see [Maintenance](./setup.md#maintenance) for the commands).
2. Unless you customized them, take the template's version of these files when resolving conflicts:
   - `.github/workflows/*`
   - `terraform/*.tf`, `terraform/.terraform.lock.hcl`, `terraform/www-redirect.js` and `terraform/bootstrap/*`
   - `lambda/**` and `shared/**`
   - `analytics/**`, except your `analytics/.env`
   - `package.json`, `pnpm-workspace.yaml` and `pnpm-lock.yaml`
3. V3.1 deletes the files below. If you changed any of them, the merge reports a conflict; delete them anyway.
   - `lambda/build/`, every `build.config.json` and `lambda/functions/www-redirect/`. Each Lambda now has its own `build` script, and Terraform zips the output.
   - `terraform/package.json` and `terraform/bootstrap/forcefully-unlock.sh`
   - `client/src/utils/customEl/`, `client/src/utils/guards.ts`, `throttle.ts`, `debounce.ts` and `ids.ts`
   - `client/src/components/Nav/utils/use*.ts`. They're replaced by `init*.ts` files in the same folder.
   - `analytics/lib/etl/` and `analytics/lib/files.ts`
   - `dev-api/nodemon.json`, `dev-api/utils/` and `dev-api/routes/contact/`
4. Run `pnpm install` from the repo root.
5. If you run Terraform locally, run `terraform init -backend-config=state.config` in `terraform/` to install the `hashicorp/archive` provider.

## Step 2: Update Your Client Changes

Skip this step if you only edited `client/src/content/index.ts`.

1. **Custom elements:** the `customEl` helper and its `props` are gone. Interactive components are now plain custom elements, with setup in `connectedCallback()` and registration with `customElements.define("my-element", MyElement)`.
   - To pass frontmatter values, export an `ElementProps` type from the frontmatter, spread `elementProps<ElementProps>({ ... })` onto the element, and extend `PropsElement<ElementProps>` in the `<script>` to read them as typed `this.props`. [SnowParticles.astro](../client/src/components/SnowParticles/SnowParticles.astro) shows the pattern. Elements without frontmatter values extend `HTMLElement`.
   - `pnpm build` now runs `astro check` first (also available as `pnpm typecheck`), so a misspelled, missing or mistyped value fails the build.
   - Don't import from `@/content` inside a `<script>`. Everything the import pulls in is bundled into the page's JavaScript, including your site text.
2. **Moved or renamed:**
   - `getAnalyticsAttribute` moved from `@/utils/analytics` to `@/utils/analyticsAttribute`.
   - The Nav helpers `useScrollSpy`, `useMobileMenu` and `useNavbarAnimation` are now `initScrollSpy`, `initMobileMenu` and `initNavbarAnimation`. `useNavbar` was merged into [Nav.astro](../client/src/components/Nav/Nav.astro).
3. **Props:**
   - `Section` no longer takes a `solidBackground` prop. It reads `solidBackground` from the section in your content.
   - `SnowParticles` no longer has a default config, so its `config` prop is required.
4. **Sections:** the `Sections` type in [types.ts](../client/src/content/types.ts) now lists its keys (`INTRO`, `PROJECTS`, `SKILLS`, `CONTACT`), so a misspelled section name is a type error. If you added a section, add its key there.
5. **Analytics endpoint:** the client always sends analytics to `/api/ingest` and no longer reads `PUBLIC_API_INGEST_ENDPOINT`.

## Step 3: Update the Analytics Dashboard

1. Remove `AWS_S3_BUCKET_PATH_PREFIX` and `CONCURRENCY` from `analytics/.env`. They're no longer used.
2. Optional: delete `analytics/.data` to start with an empty database. The dashboard now stores events in a new `events_v1` table, and the old table is left unused.
3. Start the dashboard and click `Sync`. It replaces the `Force Refresh` checkbox and imports every event file in S3 that it hasn't imported before. See [Using the Dashboard](./analytics.md#using-the-dashboard).
   - You may see more events than with V3.0. The V3.0 import only read the S3 folder named after each day, but the processor saved events in the folder for the day it ran, so some events were never imported.

## Step 4: Deploy

1. Check your deploy role and secrets:
   - If you restricted the deploy role's permissions, it needs to create and run CloudFormation change sets. The bootstrap step now uses `aws cloudformation deploy`.
   - The `AWS_DEFAULT_REGION` repository secret must match `region` in `terraform/state.config`. The bootstrap step now reads its region from `state.config`.
2. Merge your branch into `main`. The "Build and Deploy" workflow builds the Lambdas, applies Terraform, then builds and uploads the site.
   - If you deploy by hand, keep that order. The V3.0 processor drops events from the V3.1 site, because they no longer have an `offsetMs` field.

### What the First Apply Changes

Expect only in-place updates. If a plan shows a resource being replaced or destroyed, stop and check before applying.

- **Updated in place:**
  - Both analytics Lambdas get new code. Terraform now builds their zip files with `archive_file`.
  - The API Gateway API: its CORS settings are removed. The site and the API share a domain, so CORS isn't needed.
  - The API Gateway stage: throttling becomes a single default of 50 burst and 10 requests per second, the limits the ingest route already had.
  - The `www` redirect CloudFront Function: redirects now keep the query string.
- **Removed:** the `ingest_endpoint` Terraform output.

### Changes in Behavior

- **Deploys:** every push to `main` runs the whole workflow, including docs-only pushes. There's no more change detection or `force_invalidation` input.
- **State locks:** the workflows no longer delete the Terraform state lock after each run, and destroy no longer skips locking. If a run is cancelled mid-apply, see [Stuck State Lock](./deployment.md#stuck-state-lock).
- **Analytics timestamps:** each event gets the time the ingest Lambda received its batch, up to about 5 seconds after the event happened. Events in the same batch share a timestamp.
- **Analytics storage:** the processor saves each event in the S3 folder for the UTC date it happened. Files saved by V3.0 may be in the next day's folder. The dashboard doesn't depend on folder names.
- **dev-api:** runs with `node --watch` instead of `nodemon`, and its routes are listed in [dev-api/index.js](../dev-api/index.js).

## Post-Upgrade Checks

1. Open `https://www.<your-domain>/?test=1`. It should redirect to `https://<your-domain>/?test=1`.
2. Browse your site. The processor runs once a day shortly after midnight UTC, so the next day, click `Sync` in the dashboard and confirm your visit appears.
3. In the Actions tab, confirm the "Setup Terraform State Backend" step succeeded.
